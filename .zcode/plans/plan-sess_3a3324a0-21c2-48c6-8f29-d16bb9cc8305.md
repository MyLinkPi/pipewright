# 平台内置本地 Registry:构建产物统一推送 + 上游可切换 + daemon.json 统一下发

## 架构总览
在**控制机本机 docker** 上由 pipewright 自管一个 registry 栈(两个 `registry:2` 服务,compose 声明式管理):
- **制品 registry(默认 :5000)**:收构建产物 push;部署机从这里 `docker pull <addr>:5000/<slug>:<tag>` —— 补上现有缺口(环境未绑 ImageRegistry 时产物是本地 tag,远程部署 pull 必败,`internal/build/builder.go:357-373,452-485`)
- **缓存 registry(默认 :5001)**:pull-through 模式代理上游(`REGISTRY_PROXY_REMOTEURL`,默认 registry-1.docker.io,可切 DaoCloud/阿里云/自定义)。**切上游只改此配置并重建这一个容器,生产机零改动**
- pull-through 模式只读不能收 push,所以必须双服务(pull-through cache 不能 push)

各机 **daemon.json 只需配一次**:registry-mirrors→`http://<addr>:5001`、insecure-registries→`<addr>:5000,5001`(明文 HTTP,已确认)。机器从此不再随上游变化改动。

## 已确认决策
registry 部署在**控制机本机**(仿 `execCommander`/`ServiceRunner` 本地容器先例,`internal/build/driver.go:53-57`、`services.go:33-60`);协议**明文 HTTP + insecure-registries**;镜像清理做**自动保留策略**;daemon.json **手动勾选下发、整文件生成覆盖(先备份)、自动重启 docker、含控制机本机**(沿用前次确认);下发唯一触发方式是用户显式勾选确认,保存配置不触碰机器。

## 后端

### 1. 迁移 `0053_registry_config.sql`(sqlite+mysql,单例仿 `0011_ai_config.sql`)
`registry_config(id=1)`:`enabled`、`external_addr`(机器可达的控制机地址,默认自动探测出网网卡 IP,可改)、`upstream_url`(缓存上游,预置 Hub/DaoCloud/自定义)、`artifact_port`/`cache_port`(默认 5000/5001)、retention 两字段(`keep_per_project` 每项目保留最近 N tag、`max_age_days`)、时间戳。

### 2. 新包 `internal/registryhub`
- **config.go**:单例 Get/Save(仿 `internal/ai/ai.go`);校验 external_addr 主机[:端口]、upstream URL http(s)、端口范围、retention 数值。
- **stack.go**:本地栈生命周期——渲染 compose YAML(两服务+卷 `/var/lib/pipewright/registry/{data,cache}`)→ 本地 `docker compose up -d`(compose 探测仿 `server_stacks.go:565-575`);启用时部署、配置变更时重建;Status()=容器状态 + 本地 `/v2/` 探活 + 数据目录磁盘用量。
- **registry client**:走 registry HTTP API(v2 catalog / tags list / manifest 查询含创建时间 / DELETE by digest),供保留策略用。
- **retention.go**:规则计算(每项目按 manifest 时间留最近 N 个、超 X 天的删除,仿 `internal/retention` 配置模式)+ 执行(DELETE manifest 后 `docker exec registry registry garbage-collect`);周期调度跟随现有 retention 定时器位置(main.go),提供手动触发入口。
- **daemon.go**:生成 daemon.json `{"registry-mirrors":["http://<addr>:<cache_port>"],"insecure-registries":["<addr>:5000","<addr>:5001"]}`;Applier 步骤与前次方案一致:探测 docker → 备份(`daemon.json.bak.pipewright.<ts>`)→ 写临时文件 → `dockerd --validate`(可用时)→ 原子 mv → `systemctl restart docker` → 轮询 `docker info` 验证生效 → 返回逐台结果;远程经 `target.Service.Exec/Upload`,本机 `os/exec`+`os.WriteFile`;批量并发 4、单目标超时 120s;仅 enabled 时允许下发。

### 3. 构建接入(修改 `internal/build/builder.go`)
`resolveRegistry`:环境**未绑定** ImageRegistry 且内置 registry enabled → 返回内置 registry(URL=`<external_addr>:5000`,无凭据跳过 login)→ 自动 push,`artifact.Reference` 变为可跨机 pull 的地址;环境**显式绑定**外部仓库时优先(现有机制不变);disabled 时保持现状本地 tag。

### 4. HTTP API(`internal/httpapi/registry_hub.go`,仿 `ai_settings.go`)
- `GET/PUT /api/settings/registry`(CSRF 写)——只写库不下发
- `POST /api/settings/registry/deploy`(CSRF)——部署/更新栈
- `GET /api/settings/registry/status`、`POST /api/settings/registry/prune`(手动清理)
- `POST /api/registry/daemon-apply`(CSRF)——`{serverIds:[], includeLocal}` 只处理显式勾选目标
- `GET /api/registry/inspect?serverId=<id|local>`——读该机当前 mirrors 现状
- 装配:`router.go` Option + `cmd/pipewright/main.go` 注入(db + targetSvc + recorder);审计新增 `registry_deploy` / `registry_daemon_apply` / `registry_prune` action(`internal/audit/audit.go` 只增枚举)

## 边界与风险
- 控制机成为镜像中枢:构建/部署依赖其在线;磁盘用量在状态页展示
- registry:2 镜像首次部署需控制机能直连上游拉取(自举鸡生蛋,部署前不依赖缓存);之后控制机自身 daemon.json 也可指向缓存
- gc 运行期间 push 可能短暂冲突:低频周期(每日)+ 失败下轮重试
- 缓存 registry 仅代理单一上游(Docker Hub 系);quay/gcr 等不走缓存(一期)
- daemon.json 整文件覆盖有丢机器特有配置风险(已确认接受,备份兜底可回滚)
