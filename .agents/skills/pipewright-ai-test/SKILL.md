# Pipewright AI Test 需求编写

把用户的业务要求改写成 AI 可以亲自执行、观察并判定的 Markdown 需求。AI 是测试执行者，不需要生成 Playwright、JUnit 或其他自动化测试脚本。

## 工作流程

1. 用户已经给出完整场景、操作和验收标准时，直接编写，不必扫描功能代码。只查看目标目录中已有需求，沿用目录、语言和写法；首次使用时创建所需目录。
2. 信息不足时，再有针对性地阅读相关功能代码或文档。不要编造页面、接口、字段、控件名称或业务规则；关键行为无法确认时，向用户澄清，或在交付中明确列出待确认项。用户给出的验收标准与代码现状不一致时，指出冲突，不要自行改写其中一方。
3. 直接创建或修改需求文件。除非用户要求，否则不要额外输出测试计划、设计文档或流水线配置。
4. 完成后按本文末尾的清单检查本次涉及的全部需求。

## 文件与目录

- 需求放在 `.pipewright/tests/requirements/**/*.md`，正文使用自然语言，不能为空。
- 一个文件聚焦一个完整场景，可以包含该场景紧密关联的成功与失败分支。
- 按业务或执行范围划分子目录，例如 `web/`、`api/`、`smoke/`、`full/`。目录只是组织和过滤手段，不发明标签机制。
- 优先让每条需求自包含，自行准备并清理数据，不依赖其他需求留下的数据。

## 正文写法

写清楚 AI 需要做什么，以及看到什么才算通过。根据场景包含以下内容，不必机械地使用固定标题：

1. **前置条件**：测试账号或角色、起始页面、已有数据、接口认证前提。
2. **操作**：按业务顺序描述网页操作，或给出接口方法、路径和必要请求内容。
3. **预期结果**：必须能从页面文本/状态或接口状态码、响应字段中观察并判断。
4. **清理**：创建订单、资源或其他持久化数据时，说明删除、取消或恢复方法。

遵循这些原则：

- 使用具体、可观察的描述，例如“页面提示‘券码无效’，订单合计仍为 95 元”，不要只写“功能正常”“提示合理”。
- 网页需求优先使用用户可见的按钮名称、页面文案和业务状态，不要求 AI 依赖 CSS、XPath 或内部实现。
- 接口需求写清方法、路径、关键请求参数，以及预期状态码和关键响应字段；不要只写“测试创建接口”。
- 只验证 AI 能通过网页或 HTTP 实际观察到的结果，不要求查询数据库、查看服务日志或检查内部状态。
- 测试数据使用明确的名称或值。并行或重复运行可能冲突时，要求使用带随机后缀的唯一名称。
- 使用专用、低权限的测试账号和测试数据。不要把生产密钥、真实用户数据或不必要的凭据写入仓库；缺少密码等必要信息时使用明确的待填占位并提醒用户，不虚构平台凭据注入能力。
- 涉及支付、删除、消息发送等操作时，限定允许的测试范围，并写明避免真实副作用的方法和清理步骤。

## frontmatter

frontmatter 整体可省略。需要时放在文件最顶部，只使用以下字段：

```markdown
---
id: checkout-coupon
severity: blocker
target: "${BASE_URL}"
needs: [login-success]
---

在这里写测试需求正文。
```

| 字段 | 规则 |
|---|---|
| `id` | 显式 ID 最长 128 个字符且不能包含空白，并在本次发现的所有需求中唯一。建议使用稳定的英文 kebab-case。省略时由需求路径生成默认 ID；其他需求需要引用它时再显式填写。 |
| `severity` | 只能是 `blocker` 或 `suggest`，默认 `blocker`。它表示报告中的重点程度，不会把 AI 裁决变成自动放行或阻塞。 |
| `target` | 可选的被测系统地址，支持 `${VAR}`。需求中的值优先于节点默认地址；两处都为空或变量未解析时，需求无法执行。多条需求共用节点地址时省略此字段。 |
| `needs` | 可选的前置需求 ID 列表，只控制执行顺序。被依赖需求失败时，当前需求会跳过。 |

`needs` 引用的是**需求 ID**，不是文件名、流水线节点 ID 或节点名称。引用的需求必须在本次过滤出的需求集合中，且不能形成循环。

创建、验证、删除属于同一数据生命周期时，优先合并成一条自包含需求，不要为了拆文件而引入跨需求数据传递。

## 示例

### 网页需求

```markdown
---
id: web-checkout-coupon
severity: blocker
---

使用测试账号登录商城，将任一在售商品加入购物车并进入结算页。

1. 输入有效优惠券 COUPON-6，点击“使用”。
2. 记录优惠金额和订单合计。
3. 再输入无效优惠券 INVALID，点击“使用”。

预期结果：
- 使用 COUPON-6 后，页面显示优惠金额为 6 元，订单合计比原价减少 6 元。
- 使用 INVALID 后，页面提示“券码无效”，订单合计不发生变化。

不要提交真实支付。测试完成后取消未支付订单。
```

### 接口需求

```markdown
---
id: api-create-project
severity: blocker
target: "${BASE_URL}"
---

使用测试管理员身份调用 POST /api/projects，请求体包含：
- name：以 ai-test- 开头的唯一项目名称
- description：AI 测试创建的项目

预期结果：
- 响应状态码为 201。
- 响应中的 name 和 description 与请求一致。
- 使用响应返回的项目 ID 调用 GET /api/projects/{id}，状态码为 200，返回同一个项目。

最后调用 DELETE /api/projects/{id} 清理项目，并确认再次 GET 时返回 404。
```

示例只展示写法。处理真实仓库时，以实际页面、接口和业务规则替换示例内容。

## 修改与审查现有需求

- 保留仍然有效的场景，不要因为改写措辞而无意删除验收点。
- 功能行为变化时，同步更新操作、预期结果、目标地址和依赖关系。
- 检查默认 ID 与显式 ID 的冲突，不要只检查显式填写的 ID。
- 修改显式 ID 后，同步更新所有 `needs` 引用。
- 缩小 `filter` 可能使依赖需求不在执行集合中；拆分冒烟与全量目录时尤其要检查这一点。
- 不编造需求校验 CLI。需要验证行为时，使用仓库已有的解析测试或实际 AI 测试运行。

## 完成前检查

- [ ] 文件位于 `.pipewright/tests/requirements/**/*.md`，正文非空。
- [ ] 每条需求都有明确操作和可从网页或 HTTP 响应观察的预期结果。
- [ ] 页面、接口、字段、测试数据和业务规则均有依据，没有凭空假设。
- [ ] `id` 合法且在执行集合内唯一，`severity` 取值正确。
- [ ] 每条需求能取得有效 `target`，没有遗留未确认的占位符。
- [ ] `needs` 引用存在、无循环，并尽可能保持需求自包含。
- [ ] 持久化数据有清理步骤，危险操作有明确边界。
- [ ] 没有生成测试脚本、内部设计说明或用户未要求的流水线配置。
